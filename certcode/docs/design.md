# certcode 设计说明:印刷证书的离线密码学防伪码

## 1. 威胁模型

### 要防的攻击
1. **内容篡改**:拿到真证书后改姓名、编号、成绩再打印(当前主要威胁,核验只能靠电话)。
2. **整块伪造**:私钥泄露后,攻击者自行签发以假乱真的新证书。
3. **复印/传真/拍照翻拍**:防伪码经历打印 → 复印 → 传真 → 手机拍照等模拟信道后严重退化。

### 不防的(明确边界)
- 持证人本人真实证书的原件转让(身份核验是另一层问题)。
- 根密钥本身泄露——根密钥必须离线仪式化保管,这是整个体系的信任锚。
- 核验端 App 被逆向替换——App 须由认证机构签名分发,根公钥内置在 App 中。

## 2. 整体架构

```
┌──────────────────── 发证侧(内网/离线) ────────────────────┐
│                                                             │
│  根密钥 root(Ed25519,离线仪式机,永不联网)                  │
│    ├─ 签名 签发公钥目录 directory(active/compromised)       │
│    └─ 签名 签发清单 manifests(每张真证书的摘要)             │
│                                                             │
│  签发密钥 issuing key(Ed25519,可有多把,支持轮换)          │
│    └─ 对证书规范记录签名 → 二维码 payload → 印刷             │
│                                                             │
└──────────────────────────────┬──────────────────────────────┘
                                │ 定期导出(只含公钥+签名文件)
┌──────────────────────────────▼──────────────────────────────┐
│  核验侧(手机 App / 办公机,完全离线)                        │
│    扫码 → 解析信封 → Ed25519 验签 → 清单摘要比对 → 结论     │
└─────────────────────────────────────────────────────────────┘
```

## 3. 数据格式

### 3.1 证书记录(定长规范二进制,签名覆盖的内容)

```
[0]      version   u8   = 0x01
[1..17]  serial    16B  证书编号,ASCII 右补 0x00
[17]     name_len  u8   姓名 NFC UTF-8 字节数
[18..]   name      变长 姓名(NFC 规范化)
[..+16]  subject   16B  科目,ASCII 右补 0x00
[+2]     score     u16  成绩(0..=1000,支持一位小数)
[+4]     issued_on u32  签发日(纪元天数)
```

- **为什么不用 JSON/Protobuf**:JSON 字段顺序、空白、Unicode 编码形式都会让"同一记录"产生不同字节,签名失配;定长头部 + 显式长度前缀让编码唯一、解码严格(拒绝尾部多余字节和补位污染)。
- 姓名录入时做 **Unicode NFC**,避免组合字符差异导致同姓名签名不一致。
- 典型记录 52~68 字节。

### 3.2 签名信封(二维码 payload)

```
0xC0(魔数) | 0x01(信封版本) | key_id(u8) | 规范记录 | Ed25519 签名(64B)
```

- 签名前加域分离前缀 `certcode.io/signed-cert-record/v1`,防止签名被跨系统复用。
- 典型总载荷 **约 113 字节**,QR H 级纠错下为 **V10**(V10-H 字节容量 122)。
  V10 每边 57 模块 + 8 模块静区,module_px=10 时物理图 650×650px,300dpi 约 55mm 见方。
- `key_id` 让核验端知道用目录里哪把公钥,也支撑密钥轮换。

### 3.3 信任包(根签名,分发到核验端)

```
root.json                 根公钥(内置/随 App 分发)
directory.signed.json     签发公钥目录(根签名)
manifests/*.signed.json   签发清单(根签名,按 key_id 分组)
```

**目录条目**:`key_id / 公钥 / status(active|compromised) / valid_from / valid_to`。

**清单条目**:某把密钥一个编号区间内,每张真证书的编号 + 记录摘要前 10 字节
(SHA-256 截断,2^80 碰撞空间,定向伪造不可行;百万证书约 22 MB)。
清单中编号按字典序升序排列,核验端用二分查找定位,不依赖编号字符集或连续假设;
加载时校验排序、去重、区间端点与数量一致性。

所有签名对象使用**规范 JSON**(键排序、无空白)后再签,保证不同机器上可复现。

## 4. 核验逻辑

```
扫码得 payload
  ├─ 魔数/版本检查 → 不符直接 REJECTED
  ├─ 按 key_id 查根签名目录 → 无此密钥 REJECTED
  ├─ Ed25519 验签(目录公钥) → 失败 REJECTED(内容被改)
  ├─ 查签发清单:编号区间定位 + 10B 摘要比对
  └─ 结合密钥状态:
       active + 清单命中        → VERIFIED
       active + 清单未命中      → UNTRUSTED(新证清单未发布,或可疑)
       compromised + 清单命中   → VERIFIED(旧真证继续有效)
       compromised + 清单未命中 → REJECTED(泄露密钥的伪造件)
```

App 屏幕显示解码出的姓名/编号/成绩,由核验人**肉眼比对**纸质内容;
密码学保证的是"码内字段未被篡改且确认真实签发"。

## 5. 私钥泄露处置流程(关键需求)

1. 确认泄露后,在离线仪式机执行 `revoke --id N`(状态单向 active → compromised)。
2. 先 `publish-manifest` 发布该密钥**全部历史证书**的签发清单(必须在废止前/同时完成,清单是旧证存活凭证)。
3. `publish-directory` 重新发布根签名目录。
4. `export-bundle` 导出新信任包,推送/随 App 更新到全部核验端。

效果:
- 旧证书:签名有效 + 清单有摘要 → **继续 VERIFIED**,存量证书无需重印。
- 攻击者用泄露私钥签的任何新证书:清单无摘要 → **REJECTED**。
- 攻击者改旧证内容:Ed25519 验签先失败 → **REJECTED**。
- 新发证:启用新 `key_id` 的签发密钥,旧密钥自然淘汰。

## 6. 抗模拟信道退化的工程措施

| 环节 | 措施 |
|---|---|
| 纠错码 | QR 规范最高级 **EcLevel H**(Reed-Solomon,30% 容量纠错) |
| 模块尺寸 | `module_px` 默认 10px;300dpi 下每模块 ≥ 0.85mm,覆盖多个印刷网点 |
| 静区 | 强制 4 模块 quiet zone |
| 冗余印刷 | 建议证书上印**两个相同码**,任一存活即可核验 |
| 版本上限 | 自动选最小版本并限制在 V10(`DECODER_SAFE_MAX_VERSION`);超尺寸报错而非静默升级 |
| 解码端 | rqrr 自适应阈值 + 检测失败时 2x 放大重试;**必须用 `decode_to` 取原始字节**(见下) |

### 解码端关键实现细节(rqrr 踩坑记录)

rqrr 的 `Grid::decode()` 返回 `(MetaData, String)`,内部强制 `String::from_utf8`。
本系统载荷含 64 字节 Ed25519 签名,是高熵随机字节、并非合法 UTF-8,
用 `decode()` 会稳定报 `EncodingError`——与图像质量无关,极易被误判为"码面退化"。
正确做法是调用 `Grid::decode_to(&mut Vec<u8>)`,它把纠错后的原始字节直接写入
`Write`,不做任何字符集转换。所有二进制 QR 载荷的 Rust 实现都应注意这一点。

`src/degrade.rs` 提供确定性退化模拟器(高斯模糊、加性噪声、8×8 块量化、
阈值抖动二值化、亮度/对比度偏移),测试覆盖轻/中两级退化后仍可解码验签。

### 实测鲁棒性包络(module_px=10,V10-H,见 `tests/envelope.rs`)

固定其余参数单独扫描,解码仍成功的边界:

| 退化维度 | 实测安全边界 | 典型办公场景量级 |
|---|---|---|
| 高斯模糊(失焦) | σ ≤ 3.0px(约模块宽 30%) | 复印 σ≈1~2 |
| 加性噪声 | σ ≤ 50/255 | 扫描噪声 σ≈8~20 |
| 二值化阈值抖动 | ±60 | 传真机 ±10~30 |

结论:真实复印/传真(对应本模拟器的轻/中级)稳定可解;唯一悬崖是**严重失焦**
(模糊 σ≈4,约模块宽 40%),靠增大 `module_px` 或要求重新对焦拍摄解决。
注意突发聚集型错误(连片模块翻转)对 RS 块纠错的杀伤力远高于同 BER 的均匀错误,
因此全局模块误码率不能单独作为可靠性指标。

### 冗余印刷与独立失效

建议证书上并排印**两个相同码**(`qr::render_dual_png`)。两码空间分离,
物理复印/拍照时损伤相互独立:单码存活率 p 时整体可核验率 1−(1−p)²。
注意模拟器若对整图用同一种子会产生完全相关的损伤(测试伪影),
`tests/dualcode.rs` 对左右码分别用独立种子退化以还原真实的空间非均匀性。

实测建议:上线前用真实复印机/传真机/手机做物理回归。
若重度退化失败率高,优先增大 `module_px`、降低 QR 版本(缩短姓名或换 BLS 签名)。

### 可选升级:BLS 签名与解码后端
Ed25519 签名 64B。若需进一步缩小码面积,可换 BLS12-381(BLS min-pk G1 签名 48B,
省 16 字节,可从 V10 降到 V9),代价是配对运算依赖更重、核验略慢。
当前实现把签名长度做成常量 `SIGNATURE_LEN`,信封格式预留了版本号,可平滑替换。
`DECODER_SAFE_MAX_VERSION` 的 V10 上限是针对 rqrr 的保守取值;生产手机 App 换用
ZXing/ML Kit/Apple Vision 等成熟后端后可放宽,届时也可承载更长姓名。

## 7. 运维与仪式安全

- 根密钥:硬件安全模块或离线专用机,双人分权,生成后公钥哈希书面留档。
- 签发私钥:文件权限 0600(工具自动设置),建议也迁移到 HSM/USBKey。
- 清单发布节奏:建议每日/每周批量发布;两次发布之间签发的新证在核验端显示 UNTRUSTED 而非 VERIFIED,这是有意的保守策略。
- 编号规则:全局唯一、同宽度(便于区间管理);清单显式存储编号数组并按字典序排列,
  核验用二分查找,不要求编号纯数字或严格连续,跳号/字母编号都能正确定位。
- 信任包更新:核验端每次启动比对目录 `generated_on`,过期超阈值时提示更新(仍可离线核验,只是清单可能滞后)。

## 8. 命令速览

```bash
# 发证侧(离线机)
certcode root-init --dir ./ca
certcode issuer-init --root-secret ./ca/root.secret.json --id 1 \
          --dir ./ca --valid-from 2026-01-01 --today 2026-11-24
certcode issue --issuer-secret ./ca/issuers/key1.secret.json \
          --serial CERT2026000001 --name 张三 --subject WELDER-1G \
          --score 955 --date 2026-11-24 --out code.png
certcode stage  --root-secret ... --dir ./ca --envelope code.envelope.b64
certcode publish-manifest --id 1 --today 2026-11-24 ...
certcode revoke --id 1 ...          # 泄露处置
certcode publish-directory ...
certcode export-bundle --dir ./ca --out ./bundle

# 核验侧(离线)
certcode verify --bundle ./bundle --image photo.jpg --today 2026-11-24
```

退出码:`0` VERIFIED,`1` REJECTED,`2` UNTRUSTED,便于集成到批量核验流水线。
